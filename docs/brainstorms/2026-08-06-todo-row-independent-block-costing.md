## 1. 先说清楚：你看到的症状，本轮已经修了

Wendi 2026-08-05 原话：

> 打开第一行 to do list，然后点击回车换行，第二行实质上已经是另一个 block 了，但是选中深色的其实还是和上一行连成一起的。

**这条是真 bug，本轮已修**，不需要动架构就能修。根因很小：编辑态的那层浅灰底色，画的位置挂在整张列表
（`<ul>`）身上，而不是你正在编辑的那一行上。实测数据——三行列表、光标停在第 2 行，承载底色的元素是整个
UL、高 93.6px，罩住 3.3 行；同一份文档里点进一个普通段落，底色元素就是那个段落自己、高 28px，不多不少。
**列表是全编辑器唯一一个「高亮范围 ≠ 正在编辑的东西」的块类型。**

所以「第二行和上一行连成一起」是画错了地方，不是模型没拆开。修完之后底色只跟着当前行走。

同时说明另一件事：**你能观察到的行为，本轮之后已经 100% 是行级的**——悬停手柄、拖拽重排、手柄菜单、
gutter「+」、Esc 分级、⌘A 分级、行首退格剥离，加上这次的编辑态高亮。磁盘上那份 HTML 文件里仍然是一张
完整的 `<ul>`，但那是文件长什么样，你在编辑器里碰不到它。

下面这份成本单回答的是另一个问题：**如果真要把磁盘也拆成「每行一个块」，要付什么**。

## 2. 三笔成本

### 2.1 编号列表会变成「1. 1. 1.」

**用户会遇到什么**：编号列表（1. 2. 3.）每行独立之后，每一行都是一张独立的编号表，各自从 1 开始数。
屏幕上就是一串「1. / 1. / 1.」。

**为什么救不回来（现在）**：编号是浏览器自己数的，我们没写任何接管逻辑——`src/editor/blockedit.js` 的
`BASELINE_CSS` 里 `ol` 不写 `list-style-type`，全仓零 `counter-reset`。要让 N 张相邻的表接着数，得给每一行
写上「我从第几号开始」（`start=N`），并且**每次插入、删除、拖拽之后把整列重编一遍**。仓里没有这套机制，
而且 `docs/features/todo-list.md` 在做单行「转为」时已经把「按拆分位置重算 start」明确记为
「复杂度不匹配收益，留作后续」——同一个坑，那次绕开了。

### 2.2 子项（缩进的下一级）没地方放了

**用户会遇到什么**：一行下面挂子行，靠的是 HTML 的嵌套结构（列表里再套一张列表）。一旦每行都是一张独立
的表，行与行之间就全是平级兄弟，**没有任何结构能表达「这行是那行的子项」**。

**为什么这笔特别贵**：要表达层级只剩一条路，给行加一个「缩进级别」的属性。但这正是两周前刚拍死的东西——
`docs/schema-1-draft-v0.md` §1.3 的拍板原文写得很直白：缩进原语 `ws-indent-*` 是给正文 / 标题 / 引用 /
callout 用的例外，**「列表 / toggle 的层级仍只用 DOM 嵌套」**（Colin 2026-07-24）。代码里也是照这条实现的：
`ws-indent-*` 的作用域硬编码在 Tab 分支的 `text` / `heading` / `quote` / `.ws-callout` 四类上。

所以这一笔的真实代价不是写代码的工作量，是**重新打开一条刚拍板的 Schema 规则**。

### 2.3 用别的工具动过文件之后，行会静默塌回一整张

**用户会遇到什么**：Wordspace 的文档也能存成 markdown。一份「每行独立」的列表存成 md、再用别的编辑器
（Typora / VS Code / GitHub）打开保存一次、回到 Wordspace——N 个独立行会塌成一整张列表，而且**没有任何
提示**。

**两个具体机制**：

- `src/main/md-adapter.js` 的 `REPRESENTABLE` 白名单里，`ul` / `li` 是**零允许属性**的。行的 ul 一旦带
  class（比如用来表达嵌套）、或者 li 带 id（文档互链的锚点要用），整张表就降级成「HTML 岛」——在 md 文件
  里以裸 HTML 块的形式存在，不再是 markdown 列表。`test/md-adapter.test.js` 的既有断言会当场红。
- 相邻的多张单项列表在 markdown 里**只靠 marker 交替**才不合并（`- / * / -`，编号列表是 `1. / 2) / 3.`）。
  我们自己写出去再读回来是不动点，这个实测过、没问题；但外部编辑器和格式化工具会把 marker 统一成一种，
  一统一，md 层就把它们合成一张列表了，回到 app 就是 N 个块塌成 1 个。

第二条是**单向且静默**的：文件在别的工具里看起来一切正常，结构损失只在回到 Wordspace 时体现，而且没有
任何东西能提示用户「你刚才丢了结构」。这跟「本地 HTML / markdown 文件，随便用什么工具打开」这条产品承诺
是正面冲突的。

## 3. 对 7-23 那份 brainstorm 的两处更正

那份文档的结论（推荐方案 B）本文不推翻，但有两处论证需要修正，否则会影响这次拍板。

**(a) 方案 A 的两条路被捆在一起否决了，实际代价差一个量级。**

原文把「让 `blockOf` 对 li 破例」和「磁盘拆成 N 张单项 ul」并列成同一个「= 动脊椎」。前者确实是动脊椎——
块身份不变式、`topBlocks`、箭头导航、合并、序列化、拖拽全要重写。但后者对块模型是**零改动**：因为每张
`<ul>` 本来就是一个块，`blockOf` 一行都不用改。它的代价全在上面那三笔（编号 / 嵌套 / markdown），
不在块模型上。把两条捆在一起，会同时高估第二条的实现风险、低估它的格式风险——而恰恰是格式风险更难还。

**(b) §2 反对的那个东西，不是「每行一张 ul」。**

原文 §2 反对的是「像 Notion 那样打散成 body 层平铺的游离 `<li>`」。那条反对完全成立——游离的 `<li>`
确实违反 Schema-1 不变式 I2（`ul` / `ol` 的直接子只能是 `li`），校验器当场拒。

但「每行一张 ul」是另一回事：每一张都是完整的 `<ul><li>…</li></ul>`，合法 HTML。实测口径两条——
`src/lib/schema-validate.js` 的 `validateList` 是**逐 ul 独立校验**的，没有任何跨兄弟逻辑；
`src/editor/serialize.js` 对列表**零规范化**（不会把相邻的 ul 合并掉）。所以「每行一张 ul」是 100% 合规的。

也就是说：那条反对拦住的是 Notion 的做法，不是这个方案。这个方案真正的阻碍是 §2 那三笔，跟 Schema 合规
没关系。

## 4. 顺带答掉 Q4（悬了两周的那个开放问题）

7-23 的 Q4 问：**只给 to-do 特殊待遇，还是三种列表（bullet / numbered / todo）一视同仁？**当时判不了，
现在技术侧有答案了。

单看 to-do，markdown 往返是**干净的**：`rehypeFromWsTodo` 在转出 md 时会主动把 `ws-todo` class 删掉，
所以 to-do 行的 ul 身上不带任何属性——实测两张单项 todo ul 往返是不动点。再加上 to-do 天然没有编号，
§2.1 那笔直接不存在，§2.3 只剩 marker 合并那半笔。

所以「只给 to-do」在技术上确实比「三种一视同仁」便宜一档。Q4 不是纯口味题，有实打实的成本差。

## 5. 三个可选终态

### 选项 1 — 只 to-do，且只扁平的 to-do 行独立

**付什么**：三笔里只付 §2.3 的半笔（marker 合并）。编号、嵌套两笔都绕开了。

**残留问题**：嵌套 to-do 仍然只能是容器模型 = 同一份文档里**两套模型并存**——没有子项的行是块，
有子项的行是容器里的项。Wendi 这次报的高亮类问题会以「只在带子项的列表里出现」的形式留着，而且**更难
解释**：看起来一模一样的两行，行为不一样。将来每加一个新交互，都要先判断「这行是块还是项」。

### 选项 2 — 三种列表全量每行独立

**付什么**：三笔全付，其中 §2.2 需要 Wendi / Colin 重新打开 7-24 刚拍的 Schema 铁律。

**换回什么**：模型统一，跟 Notion 完全对等，不留分裂模型。这是唯一能真正消灭上面那个「两套模型」的选项，
也是最贵的。

### 选项 3 — 维持方案 B（本轮已交付的状态）

**付什么**：0，已经做完了。磁盘保持一张 canonical `<ul>`，交互层全部行级。

**残留问题**：将来每加一个新交互，都要单独把它下沉到行——本轮修的这个高亮，就是之前一路下沉时漏掉的
最后一处。这是**持续的边际成本**，不是一次性的。好处是每一笔都很小、且从不影响磁盘上的文件。

### 推荐：选项 3

理由是三笔成本里有两笔（编号、嵌套）买回来的东西 Wendi 看不见——她看得见的是行为，而行为本轮已经全部
对齐；第三笔（markdown marker 合并）不是成本，是**净损失**：用户拿别的工具动一下文件，结构就静默塌缩，
跟「本地文件、随便用什么工具打开」直接冲突，而且换不回任何用户可见的好处。

**如果 Wendi 判断「分裂模型」本身不可接受**（即嵌套那半也必须行级），那应该直接走选项 2，不要走选项 1。
选项 1 省下的钱，换来的是同一份文档里两套模型，长期比现在更难维护、更难向用户解释。

**需要 Wendi 回答的一句话**：除了本轮修掉的高亮，还有哪个**具体行为**让你觉得这两行仍然连在一起？
如果举不出来，选项 3 就是答案；如果举得出来，那多半又是一处漏掉的下沉，仍然不需要动架构。
